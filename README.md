# EventsWeb

Простой REST API для управления событиями, реализованный на ASP.NET Core Web API.

## Требования

- .NET 10 SDK или выше

## Запуск проекта

Клонировать репозиторий:

```bash
git clone <repository-url>
```

Восстановить зависимости:

```bash
dotnet restore
```

Собрать проект:

```bash
dotnet build
```

Запустить API:

```bash
dotnet run --project EventsWeb.Api
```

После запуска адрес приложения будет указан в консоли.

Swagger UI доступен по адресу:

```text
/swagger
```

Например:

```text
https://localhost:xxxx/swagger
```

## Запуск тестов

Для запуска всех юнит-тестов выполнить:

```bash
dotnet test
```

Тесты реализованы с использованием xUnit и покрывают основную бизнес-логику `EventService`, включая CRUD-операции, фильтрацию и пагинацию.

## API

### Получить события

```http
GET /events
```

Метод поддерживает фильтрацию и пагинацию с помощью query-параметров:

| Параметр | Тип | По умолчанию | Описание |
|---|---|---:|---|
| `title` | `string` | — | Фильтрация по названию. Поиск регистронезависимый, поддерживается частичное совпадение |
| `from` | `DateTime` | — | Возвращает события, начинающиеся не раньше указанной даты |
| `to` | `DateTime` | — | Возвращает события, заканчивающиеся не позже указанной даты |
| `page` | `int` | `1` | Номер страницы |
| `pageSize` | `int` | `10` | Количество событий на странице |

Все указанные фильтры применяются совместно.

Пример запроса:

```http
GET /events?title=meeting&from=2026-09-01T00:00:00&to=2026-09-30T23:59:59&page=1&pageSize=10
```

Пример ответа:

```json
{
  "totalCount": 2,
  "currentPageSize": 2,
  "currentPageNumber": 1,
  "entities": [
    {
      "id": "d9341ab9-e9f0-46dd-bf30-6677037d1b75",
      "title": "Project meeting",
      "description": "Sprint planning",
      "startAt": "2026-09-10T12:00:00",
      "endAt": "2026-09-10T13:00:00"
    }
  ]
}
```

### Получить событие по ID

```http
GET /events/{id}
```

Возвращает событие с указанным `id`.

`id` имеет тип `Guid`.

Если событие не найдено, возвращается:

```text
404 Not Found
```

### Создать событие

```http
POST /events
```

Пример тела запроса:

```json
{
  "title": "Название события",
  "description": "Описание (необязательно)",
  "startAt": "2026-09-10T12:00:00",
  "endAt": "2026-09-10T13:00:00"
}
```

### Обновить событие

```http
PUT /events/{id}
```

Тело запроса имеет тот же формат, что и при создании события.

Если событие с указанным `id` не найдено, возвращается:

```text
404 Not Found
```

### Удалить событие

```http
DELETE /events/{id}
```

Если событие с указанным `id` не найдено, возвращается:

```text
404 Not Found
```

### Создать бронирование

```http
POST /events/{id}/book
```

Создаёт бронирование для указанного события. При успешном выполнении возвращает `202 Accepted` с информацией о созданной брони. Новая бронь получает уникальный идентификатор и статус `Pending`.

В заголовке `Location` возвращается адрес для получения текущего состояния бронирования.

Пример ответа:

```json
{
  "id": "a4b82a15-5b0b-44d6-a2c9-d816d47c90ab",
  "eventId": "d9341ab9-e9f0-46dd-bf30-6677037d1b75",
  "status": 1,
  "createdAt": "2026-10-25T12:00:00Z",
  "processedAt": null
}
```

Если событие с указанным ID не существует, возвращается 404 Not Found.

### Получить бронирование по ID

```http
GET /bookings/{id}
```

Возвращает текущее состояние бронирования с указанным ID. При успешном выполнении возвращается 200 OK с информацией о бронировании. Если бронирование не найдено, возвращается 404 Not Found.

## Пример сценария бронирования

**1. Создать событие**

```
POST /events
{
  "title": "Project meeting",
  "description": "Sprint planning",
  "startAt": "2027-01-10T12:00:00Z",
  "endAt": "2027-01-10T13:00:00Z"
}
```

После успешного создания сервер возвращает 201 Created.

**2. Получить идентификатор события**

```http
GET /events
```

Найти созданное событие в коллекции `entities` и скопировать значение его поля ID.

**3. Создать бронирование**

```http
POST /events/{id}/book
```

id = идентификатор события.

Сервер возвращает 202 Accepted с информацией о бронировании и заголовком `Location`.

**4. Проверить состояние бронирования**

```http
GET /bookings/{bookingId}
```

Сразу после создания бронирование имеет статус `Pending` (status = 1).

**5. Дождаться фоновой обработки**

Через несколько секунд повторить запрос:

```http
GET /bookings/{bookingId}
```

После успешной обработки статус изменится на `Confirmed` (status = 2), а поле `ProcessedAt` будет содержать время подтверждения бронирования.

## Хранение бронирований

Бронирования хранятся в оперативной памяти приложения с использованием сервиса `BookingService`, зарегистрированного в DI-контейнере как `Singleton`.

Все запросы к бронированиям и фоновый сервис используют общий экземпляр `BookingService`.

Постоянное хранилище данных не используется. После перезапуска приложения все созданные бронирования удаляются.

## Модель бронирования

Бронирование представлено сущностью `Booking`, содержащей следующие поля:

| Поле | Тип | Описание |
|---|---|---|
| `Id` | `Guid` | Уникальный идентификатор бронирования |
| `EventId` | `Guid` | Идентификатор события, к которому относится бронирование |
| `Status` | `BookingStatus` | Текущий статус бронирования |
| `CreatedAt` | `DateTime` | Дата и время создания бронирования (UTC) |
| `ProcessedAt` | `DateTime?` | Дата и время обработки бронирования (UTC). До обработки имеет значение `null` |

Перечисление `BookingStatus` определяет три возможных состояния бронирования:

| Значение | Статус | Описание |
|---|---|---|
| `1` | `Pending` | Бронирование создано и ожидает обработки |
| `2` | `Confirmed` | Бронирование подтверждено |
| `3` | `Rejected` | Бронирование отклонено |

При создании бронирование автоматически получает уникальный `Id`, статус `Pending` и текущую дату в `CreatedAt`.

## Фоновая обработка бронирований

Для асинхронной обработки бронирований используется `BookingBackgroungService`, наследующий `BackgroundService` и зарегистрированный в DI-контейнере через `AddHostedService`.

После создания бронирования API немедленно возвращает `202 Accepted`, не дожидаясь завершения обработки.

Фоновый сервис работает по следующему алгоритму:

1. Получает из `BookingService` все бронирования со статусом `Pending`.
2. Для каждого бронирования выполняет искусственную задержку в 2 секунды, имитирующую обращение к внешней системе.
3. После задержки изменяет статус бронирования на `Confirmed`.
4. Записывает текущие дату и время в UTC в поле `ProcessedAt`.
5. После обработки текущей партии ожидает 2 секунды перед следующей проверкой.

На текущем этапе все ожидающие бронирования автоматически подтверждаются. Статус `Rejected` предусмотрен моделью и может быть установлен через метод `Reject`, но в автоматической обработке пока не используется.

Фоновый сервис использует общий экземпляр `BookingService`, поэтому обновлённое состояние бронирования доступно через `GET /bookings/{id}` без дополнительных действий со стороны клиента.

## Обработка ошибок

В приложении используется глобальный middleware для обработки необработанных исключений.

Ошибки возвращаются в едином JSON-формате на основе `ProblemDetails`.

Пример ответа:

```json
{
  "status": 400,
  "detail": "Описание ошибки"
}
```

Используемые HTTP-статусы:

- `400 Bad Request` — ошибка валидации;
- `404 Not Found` — запрашиваемый ресурс не найден;
- `500 Internal Server Error` — непредвиденная ошибка приложения.

Ошибки также записываются с использованием встроенного `ILogger`.
